Decision Log

ADR-style record of the significant choices behind om-cli — the options weighed, what was decided, and what it costs us.

Each entry below is a lightweight Architecture Decision Record: Context (the forces in play), Options considered, the Decision, its Consequences, and a Status of Accepted or Open. Entries are numbered ADR-NNN and are append-only — the canonical "what is true now" view lives in v0 §13; this page is the narrative of how we got there.

How to use this log

New decisions are appended here as the project evolves — never rewritten in place. To reverse a decision, add a new ADR that supersedes the old one and flip the old entry's status to Superseded with a back-reference. This preserves the historical reasoning, which is the whole point of an ADR log.

ADR-001

Use zod for tool input schemas (over valibot)

Accepted
Context

Every tool declares its input shape once, and that shape serves two masters: runtime validation of model-produced arguments before run() executes, and the JSON Schema sent to the provider so the model knows the tool's signature. We wanted a single source of truth — schema: ZodSchema<I> on the Tool<I> interface — that covers both without hand-writing JSON Schema.

Options considered
  • zod 4 — mature, familiar; ships z.toJSONSchema() so the model-facing schema is derived, not duplicated.
  • valibot — smaller bundle and faster cold start via modular imports, but a less direct JSON Schema story and less ecosystem familiarity for this team.
  • Hand-written JSON Schema + a thin runtime validator — zero schema-lib dependency, but two artifacts to keep in sync per tool and easy to drift.
Decision

Adopt zod 4. Tool authors write one ZodSchema; z.toJSONSchema produces the provider-facing schema (Anthropic input_schema / OpenAI tools[].function.parameters — see providers.html), and the same schema validates the model's arguments at the permission/execution boundary.

Consequences
  • Bun startup carries zod's parse/registration cost on every launch. Measured and deemed acceptable for a CLI; revisit only if cold start becomes a complaint.
  • Schema derivation must round-trip cleanly to both providers' JSON Schema dialects; the provider adapters own any per-provider quirk (e.g. unsupported keywords), not the tools.
  • If startup cost ever dominates, valibot remains a drop-in candidate behind the same schema field — the Tool interface does not leak zod beyond the type.

See tools.html, v0 §3 Tech Stack.

ADR-002

OpenAI integration via the Responses API (over Chat Completions)

Accepted
Context

The core consumes one Provider interface that streams a normalized ProviderEvent union (text.delta, tool_call, done). The Anthropic side is the Messages API; we needed an OpenAI surface whose streaming and tool-call shape map cleanly onto that union with the least adapter friction.

Options considered
  • Responses API — output-item model (function_call items, response.output_text.delta / function_call_arguments.delta stream events) lines up with our event union and our normalization map.
  • Chat Completions — ubiquitous and well-trodden, but its tool_calls delta-accumulation and message-role conventions are a noisier fit for the streaming tool-call model we already built for Anthropic.
Decision

Use the OpenAI Responses API behind the Provider interface. The adapter maps instructions↔system, function_call output items↔tool_use blocks, function_call_output↔tool_result, and the respective streaming delta events into our internal types.

Consequences
  • The full normalization table (see v0 §6 and providers.html) is authored against Responses semantics; switching to Chat Completions later would mean a second adapter, not a tweak.
  • Responses' optional server-side state (store / previous_response_id) is a live design choice — tracked separately in ADR-007.

See providers.html, v0 §6 Provider Layer.

ADR-003

Defer parallel tool calls; serialize tool execution in v0

Accepted
Context

Both providers can emit multiple tool calls in a single assistant turn. Executing them concurrently is tempting for latency, but it collides with two v0 invariants: every call must produce a result, and write/exec calls each route through a human approval prompt. Concurrent approvals and concurrent side effects are hard to reason about before the basic loop is proven.

Options considered
  • Sequential execution — run tool calls one at a time in emission order; each gets its own approval (if needed) and result before the next starts.
  • Parallel execution with a concurrency gate — faster for independent reads, but needs an approval-ordering policy and careful interleaving of tool.start / approval.request / tool.result events.
Decision

v0 serializes tool execution. The loop processes tool calls in order; the AgentEvent stream stays linear and the approval modal handles one request at a time.

Consequences
  • Simpler loop and TUI: a single in-flight tool card, deterministic event ordering, trivial AbortSignal unwind.
  • Latency cost when the model batches independent reads (e.g. several glob/read calls). Acceptable for v0.
  • Revisit once the loop + approval ordering are proven — likely first for the auto-allow read class, where no approval interleaving is required.

See v0 §5 Agent Loop (loop invariants), roadmap.html.

ADR-004

Exact-string edit for v0 (over line-range and unified-diff)

Accepted
Context

The agent needs to modify files. The edit primitive's failure mode matters more than its expressiveness: a wrong edit that silently corrupts a file is far worse than one that errors and asks the model to retry. We need something deterministic with zero fuzzy-applier complexity for v0.

Options considered
  • Exact-string replacement — old_string must match uniquely in a file that was read this session; otherwise the tool errors and asks the model to add surrounding context. Full-file create/rewrite goes through write.
  • Unified-diff / patch application — expressive and reviewable, but needs a (often fuzzy) patch applier and a review surface to be worthwhile.
  • Line-range editing — rejected outright: line numbers drift across multi-edit turns, inviting silent corruption.
Decision

v0 ships exact-string edit (unique match, must-have-read) plus full-file write. Unified-diff is the post-v0 path, and it lands together with the diff review UI — the diff format and the review surface are the same artifact, so building a patch applier before the loop is even proven is the wrong order.

Consequences
  • Deterministic edits; the failure mode is a clean retry, not corruption.
  • "Must have been read this session" couples edit to read-state the session must track — a small bit of bookkeeping in the tools layer.
  • Multi-occurrence targets force the model to widen context, costing a round-trip; accepted as the safe default.
  • The unified-diff migration is gated on the diff review UI shipping — see roadmap.html.

See tools.html, v0 §7 Tools.

ADR-005

No project-root path jail in v0

Accepted
Context

A coding agent reads and writes files and runs shell commands. The obvious safety reflex is to confine it to the project root. But a path jail is both leaky (symlinks, .., absolute paths, bash reaching anywhere) and frequently wrong for real work (reading ~/.config, editing a sibling repo). We needed a boundary we could actually trust.

Options considered
  • No path jail; the approval prompt is the boundary. Coarse permission classes — read auto-allows, write and exec prompt — with the human deciding on real, previewed operations.
  • Project-root jail — feels safe but gives false confidence (trivially bypassed via bash) while blocking legitimate cross-tree work.
  • Per-path write scopes / command sandboxing — stronger, but argument parsing and sandboxing are a project of their own. Deferred to post-v0.
Decision

v0 has no project-root path jail. Safety comes from the permission classes plus the approval modal (Allow once / Allow session / Deny), with a session allowlist keyed by tool + argument signature. A denied call still returns a tool result so the loop stays well-formed.

Consequences
  • Honest boundary: the user approves the actual previewed write/exec, rather than trusting a guard that bash sidesteps anyway.
  • More approval prompts in unconfigured sessions; mitigated by Allow session and config pre-allow (permissions.autoAllow / allowCommands).
  • Fine-grained per-path scopes, command-argument sandboxing, and a read-only "plan mode" are explicitly post-v0 (roadmap.html).

See v0 §8 Permissions, tools.html.

ADR-006

OpenTUI as the terminal front end

Accepted
Context

The core is deliberately UI-agnostic: it emits a typed AgentEvent async-iterable and consumes user input plus approval responses. The front end's job is to render streaming text, tool cards, and the approval bar, and to feed input back. We needed a terminal UI approach that fits a single Bun process and a reactive, mutating scrollback.

Options considered
  • OpenTUI (@opentui/core 0.3.0) — component-based terminal rendering with reactive scrollback and input, aligned with the event-stream model.
  • Hand-rolled ANSI / raw-mode rendering — maximal control, maximal effort; reinvents layout, scrollback, and input handling.
  • An Ink/React-style stack — familiar component model but a heavier runtime and a less natural fit for the Bun-native bias.
Decision

Use OpenTUI for the TUI layer. Per the milestone plan, the core is built headless first (ADR-008) and OpenTUI is swapped in at M5 over the proven event stream — making M5 the v0 definition of done.

Consequences
  • The TUI consumes the same AgentEvent stream the headless harness already exercises; the front end is additive, not a rewrite.
  • OpenTUI's handling of a long, mutating scrollback is unproven for us — captured as the open question in the open set / v0 §13, to validate at M5.

See tui.html, v0 §10 TUI Layer, v0 §4 Architecture.

ADR-007

Own conversation state; canonical internal message store (store:false)

Open
Context

om-cli keeps a canonical internal Message[] store; per-provider adapters serialize it to wire format and parse the stream back. Anthropic resends full messages[] each turn. OpenAI's Responses API offers a choice: resend full input[] with store:false (we own state), or lean on server-side state via previous_response_id.

Options considered
  • Own state, store:false — the internal store stays authoritative for both providers; conversation history is identical regardless of who answers; transcript JSONL stays the single record of truth.
  • OpenAI previous_response_id — smaller request payloads and server-managed continuity, but it makes OpenAI a stateful special case, splits the source of truth, and complicates provider-swapping mid-session.
Decision

Leaning toward owning state with store:false — to be confirmed at M4 (when the OpenAI provider lands). This keeps the canonical store authoritative, providers swappable, and the transcript complete. Status remains Open until validated against real Responses behavior and payload-size limits.

Consequences
  • Larger requests (full history every turn) on the OpenAI side — the same cost we already pay on Anthropic, so no new pattern to maintain.
  • One conversation model, one transcript, clean mid-session provider swaps; no divergence between a local store and a server-held thread.
  • If confirmed, this folds into ADR-002 and the provider layer as settled behavior; if reversed, a new ADR will record the move to server-side state.

See v0 §13 (Still open), providers.html, v0 §9 Sessions & Context.

ADR-008

Build the core headless before the TUI

Accepted
Context

The riskiest parts of om-cli are the agent loop, the provider normalization, and the permission gate — not the rendering. Coupling the loop's correctness to a terminal UI would make those hard parts harder to test and slower to iterate. The architecture already separates a UI-agnostic core (emits AgentEvent) from any consumer.

Options considered
  • Headless core first, TUI last. Prove the loop, both providers, tools, and permissions against the raw AgentEvent stream (milestones M0–M4), then add OpenTUI at M5.
  • TUI-first / co-developed — earlier visual feedback, but loop bugs and rendering bugs tangle together and the event contract gets shaped by the UI instead of the other way around.
Decision

Build core headless first. The AgentEvent async-iterable is the contract; a minimal headless consumer drives development through M0–M4, and OpenTUI is swapped in at M5 = v0 done (ADR-006).

Consequences
  • The event contract is designed for correctness and testability, not for one renderer — the TUI is a clean consumer of a stable stream.
  • Loop, provider, and permission logic are testable headlessly (script a consumer, assert the event sequence) without a terminal harness.
  • No interactive UI until M5; early milestones are validated programmatically, which is a feature, not a gap.

See v0 §12 Milestones, v0 §4 Architecture, roadmap.html.
