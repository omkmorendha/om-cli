Tools

Per-tool contracts: schemas, result shapes, previews, and shared mechanics.

zod 4 z.toJSONSchema Bun-native Draft · 2026-05-30

01 Overview

This page is the contract sheet for every v0 tool. v0 §7 defines the Tool interface and the tool set; here each tool gets its zod schema, ToolResult shape, preview() format, permission class, edge cases, and truncation behavior — followed by the shared mechanics every tool inherits.

Tools are the only side-effect surface in om-cli. The model never touches disk or spawns processes directly: it emits a tool call, the registry validates the input against the zod schema, the permission gate decides, and only then does run() execute. The schema is the single source of truth — it produces the JSON Schema the model sees and validates input before execution.

interface Tool<I> {
  name: string;
  description: string;
  schema: ZodSchema<I>;          // z.toJSONSchema(schema) -> model-facing spec
  permission: PermissionClass;    // "read" | "write" | "exec"
  preview(input: I): string;      // one-line approval/scrollback preview
  run(input: I, ctx: ToolContext): Promise<ToolResult>;
}

type PermissionClass = "read" | "write" | "exec";

interface ToolResult {
  ok: boolean;
  content: string;                // model-facing text (already truncated)
  error?: string;                 // present iff ok === false
  meta?: Record<string, unknown>; // structured extras for TUI / transcript
}
ToolPurposePermissionSide effect
readRead a file, optional line rangereadnone
lsList a directoryreadnone
globFind files by patternreadnone
grepSearch file contentsreadnone
writeCreate / overwrite a filewritedisk
editExact-string replacementwritedisk
bashRun a shell commandexecprocess
Path convention Every path argument is an absolute path at the tool boundary. v0 has no project-root jail — an out-of-root path is not rejected; it flows through the normal write/exec approval and the user is the guard. Relative paths are resolved against ctx.cwd as a convenience, then normalized.

02 read

Purpose. Read a UTF-8 text file from disk, optionally a line range. Reading a file is also the prerequisite for editing it — a successful read records the resolved path in the session read-set (see §9), which edit later checks.

schema

const readSchema = z.object({
  path: z.string().describe("Absolute path to the file to read."),
  offset: z.number().int().min(1).optional()
    .describe("1-based line to start at. Default: first line."),
  limit: z.number().int().min(1).optional()
    .describe("Max lines to return. Default: whole file (truncation still applies)."),
});

ToolResult

content is the selected lines, each prefixed with a right-aligned 1-based line number and a tab (cat -n style) so the model can quote line positions back to edit. meta carries structured extras for the TUI tool card and transcript.

// meta on success
{
  path: string;          // resolved absolute path
  lines: number;         // lines returned
  totalLines: number;    // lines in file
  bytes: number;         // bytes of content returned
  truncated: boolean;    // line-count or byte cap hit
}

preview()

read(input) => `read ${rel(input.path)}` +
  (input.offset || input.limit
    ? `:${input.offset ?? 1}${input.limit ? `+${input.limit}` : ""}`
    : "")
// e.g.  "read src/parser.ts"   or   "read src/parser.ts:40+20"

rel() renders the path relative to ctx.cwd when it is inside cwd, otherwise the absolute path — used in every preview for legibility.

Permission

read → auto-allow. No prompt.

Edge cases

  • Missing file → ok:false, error:"file not found: <path>".
  • Path is a directory → ok:false, error:"path is a directory, use ls".
  • Binary file (NUL byte in first 8 KB sniff) → ok:false, error:"binary file, not shown" with meta.bytes set; never streamed to the model.
  • Empty file → ok:true, content:"", meta.lines:0 (still records the read-set entry).
  • offset past EOF → ok:true, empty content, no error (model can infer file length from meta.totalLines).

Truncation

Two caps, whichever hits first: the explicit limit line count, and the shared byte cap (§11). On a byte cap the head+tail policy applies and meta.truncated is true.

03 ls

Purpose. List the immediate entries of a directory (non-recursive in v0). Used by the model to orient before reading or globbing.

schema

const lsSchema = z.object({
  path: z.string().describe("Absolute path to the directory to list."),
  all: z.boolean().default(false)
    .describe("Include dotfiles (entries starting with '.')."),
});

ToolResult

content is one entry per line, directories suffixed with /, sorted directories-first then lexicographically. meta.entries is the structured form for the TUI.

// meta on success
{
  path: string;                                   // resolved directory
  entries: { name: string; type: "file" | "dir" | "symlink"; size?: number }[];
  count: number;
  truncated: boolean;                             // entry cap hit (see below)
}

preview()

ls(input) => `ls ${rel(input.path)}`   // "ls src/"

Permission

read → auto-allow.

Edge cases

  • Missing directory → ok:false, error:"directory not found: <path>".
  • Path is a file → ok:false, error:"path is a file, use read".
  • Empty directory → ok:true, content:"(empty)", meta.count:0.
  • Broken symlink → listed with type:"symlink" and no size; never followed.

Truncation

Hard cap of 1000 entries; beyond that the list is cut and a notice line is appended (… +N more entries (use glob for large trees)), meta.truncated:true.

04 glob

Purpose. Find files by glob pattern using Bun.Glob. The Bun-native path-matcher; fast, no shell, no external binary.

schema

const globSchema = z.object({
  pattern: z.string()
    .describe("Glob pattern, e.g. 'src/**/*.ts'. Matched with Bun.Glob."),
  cwd: z.string().optional()
    .describe("Directory to scan from. Default: ctx.cwd."),
});

ToolResult

content is one matching path per line, sorted by most-recently-modified first (so the model sees the files most likely in play). meta carries the count and the scan root.

// meta on success
{
  pattern: string;
  cwd: string;          // resolved scan root
  matches: string[];    // absolute paths, mtime-desc
  count: number;
  truncated: boolean;
}

preview()

glob(input) => `glob ${input.pattern}`   // "glob src/**/*.ts"

Permission

read → auto-allow.

Edge cases

  • No matches → ok:true, content:"(no matches)", meta.count:0. An empty result is not an error.
  • Invalid pattern (Bun.Glob throws) → ok:false, error carrying the normalized message.
  • Missing cwd → ok:false, error:"scan root not found: <cwd>".
  • Symlink cycles are not followed; Bun.Glob does not descend into them.

Truncation

Hard cap of 1000 matches; excess is cut with a … +N more matches notice and meta.truncated:true. Because matches are mtime-desc, the cap keeps the freshest files.

05 grep

Purpose. Search file contents by regex. Uses ripgrep (rg) when it is on PATH for speed and gitignore-awareness, and falls back to a pure-Bun scanner when it is not (detection in §12). The two backends produce the same ToolResult shape.

schema

const grepSchema = z.object({
  pattern: z.string().describe("Regular expression to search for."),
  path: z.string().optional()
    .describe("File or directory to search. Default: ctx.cwd."),
  glob: z.string().optional()
    .describe("Restrict to files matching this glob, e.g. '*.ts'."),
  ignoreCase: z.boolean().default(false),
  context: z.number().int().min(0).max(10).default(0)
    .describe("Lines of context around each match (rg -C)."),
});

ToolResult

content is grouped by file, each match rendered path:line:text (context lines use - as the separator instead of :, matching ripgrep). meta records which backend ran so the TUI and transcript can show it.

// meta on success
{
  pattern: string;
  backend: "ripgrep" | "fallback";
  files: number;        // distinct files with a match
  matches: number;      // total matching lines
  truncated: boolean;
}

preview()

grep(input) => `grep /${input.pattern}/` +
  (input.path ? ` in ${rel(input.path)}` : "") +
  (input.glob ? ` (${input.glob})` : "")
// e.g.  "grep /TODO/ in src/ (*.ts)"

Permission

read → auto-allow.

Edge cases

  • No matches → ok:true, content:"(no matches)", meta.matches:0. Note: rg exits 1 on no-match — that is normalized to a successful empty result, not an error.
  • Invalid regex → ok:false with the engine's error (both backends validate up front).
  • Binary files are skipped by both backends (no NUL-byte content streamed).
  • Search root missing → ok:false, error:"search path not found: <path>".

Truncation

Cap on matches emitted (default 200 lines) plus the shared byte cap. When cut, a … +N more matches (narrow with glob/path) notice is appended and meta.truncated:true. The fallback backend enforces the same caps in-process so it never streams more than ripgrep would.

06 write

Purpose. Create a new file or fully overwrite an existing one. The path for whole-file content; partial changes go through edit.

schema

const writeSchema = z.object({
  path: z.string().describe("Absolute path to write. Parent dirs are created."),
  content: z.string().describe("Full file content (overwrites any existing file)."),
});

ToolResult

// meta on success
{
  path: string;
  bytes: number;        // bytes written
  created: boolean;     // true = new file, false = overwrote existing
}

content on success is a short confirmation, e.g. wrote 1.2 KB to src/config.ts (created). The file body is never echoed back to the model.

preview()

write(input) => `write ${rel(input.path)} (${human(input.content.length)})`
// "write src/config.ts (1.2 KB)"

Permission

write → prompt (auto-allow only if config pre-allows the class). The approval modal shows the preview() string.

Edge cases

  • Overwrite is allowed — write does not require a prior read (that prerequisite is edit's, since overwrite intentionally discards existing content). The approval prompt is the safeguard.
  • Missing parent directories are created (mkdir -p semantics) so the model need not ls first.
  • Target is a directory → ok:false, error:"path is a directory".
  • Permission denied by OS → ok:false with the normalized EACCES message.
  • Denied at the gate → still returns a ToolResult (ok:false, error:"denied by user") so the loop continues.

Truncation

None — input is taken verbatim. The success content is a fixed-size confirmation, so there is nothing to truncate.

07 edit

Purpose. Replace one exact, uniquely-matching substring in a previously-read file. Deterministic surgical edits; its failure mode is a clean retry, never silent corruption. The full algorithm is specified in §10.

schema

const editSchema = z.object({
  path: z.string().describe("Absolute path to the file to edit."),
  old_string: z.string()
    .describe("Exact text to replace. Must occur exactly once in the file."),
  new_string: z.string()
    .describe("Replacement text. Must differ from old_string."),
})
  .refine(v => v.old_string !== v.new_string, {
    message: "old_string and new_string must differ",
    path: ["new_string"],
  });

ToolResult

// meta on success
{
  path: string;
  line: number;         // 1-based line of the replaced match
  removed: number;      // bytes removed
  added: number;        // bytes added
}

content on success is a short confirmation, e.g. edited src/parser.ts at line 88. meta.line lets the TUI render a focused diff card (see the TUI mock in v0 §10).

preview()

edit(input) => `edit ${rel(input.path)}`   // "edit src/parser.ts"

The approval modal additionally renders a small -/+ diff of old_string → new_string built from the same input (see tui.html); preview() itself stays one line.

Permission

write → prompt.

Edge cases & truncation

All edge cases (read-prerequisite miss, zero matches, multiple matches) are enumerated with their exact error strings in §10. There is no output truncation — the result is a fixed-size confirmation.

08 bash

Purpose. Run a shell command via Bun.spawn. The general-purpose escape hatch (build, test, git, package managers). stdout/stderr stream live to the TUI and the AbortSignal threads through for clean Ctrl-C cancellation.

schema

const bashSchema = z.object({
  command: z.string().describe("Shell command to run via the system shell."),
  cwd: z.string().optional().describe("Working directory. Default: ctx.cwd."),
  timeout_ms: z.number().int().min(1).max(600_000).default(120_000)
    .describe("Kill the process after this many ms."),
});

ToolResult

content is the combined, ordered stdout+stderr (interleaved as produced), already truncated. ok follows the exit code: true iff exit 0. A non-zero exit is not a tool failure in the protocol sense — it is reported as ok:false with the output intact so the model can read the error.

// meta (always present, success or failure)
{
  command: string;
  cwd: string;
  exitCode: number | null;   // null if killed by signal/timeout/abort
  signal: string | null;     // e.g. "SIGTERM" on timeout/abort
  durationMs: number;
  truncated: boolean;
}

preview()

bash(input) => `bash ${oneLine(input.command, 80)}`
// "bash npm test"   (collapsed to one line, capped at 80 chars + …)

Permission

exec → prompt. The session allowlist can be keyed on the command signature (e.g. allow bash: npm test for the session without re-prompting) — see v0 §8.

Edge cases

  • Non-zero exit → ok:false, error:"exited with code <n>", full output in content.
  • Timeout → process killed (SIGTERM), ok:false, error:"timed out after <ms>ms", meta.signal:"SIGTERM", partial output preserved.
  • Aborted (Ctrl-C → ctx.signal) → process killed, ok:false, error:"aborted". The loop unwinds cleanly per the loop invariants.
  • Command not found / shell error → surfaces as a non-zero exit with the shell's stderr in content.
  • No stdin. v0 runs commands non-interactively; a process that blocks on stdin will hit the timeout.

Truncation

Shared byte cap with head+tail (§11). Live TUI streaming shows the full output as it arrives; only the model-facing content is truncated, with meta.truncated:true.

09 Shared mechanic — ToolContext

Every run() receives a ToolContext. It is the tool's only window onto session state — tools are otherwise pure functions of (input, ctx).

interface ToolContext {
  cwd: string;                 // resolved working directory for relative paths
  readSet: ReadSet;            // files read this session (edit prerequisite)
  signal: AbortSignal;         // threaded from the turn; honored by bash, read & grep
  log: Logger;                 // structured logger -> transcript + debug
}

interface ReadSet {
  add(path: string): void;     // called by read() on success (resolved abs path)
  has(path: string): boolean;  // called by edit() to enforce the prerequisite
}

interface Logger {
  debug(msg: string, fields?: Record<string, unknown>): void;
  info(msg: string, fields?: Record<string, unknown>): void;
  warn(msg: string, fields?: Record<string, unknown>): void;
  error(msg: string, fields?: Record<string, unknown>): void;
  child(scope: string): Logger;  // scoped child, e.g. ctx.log.child("read")
  close(): Promise<void>;
}
  • cwd — used to resolve relative path arguments and to render rel() in previews. The session sets it once at startup; v0 has no per-turn cd persistence (a bash cd does not move ctx.cwd).
  • readSet — the session-scoped set of files that have been successfully read. read.run() calls add(resolvedPath); edit.run() calls has(resolvedPath) as its first gate (§10). It lives on the Session and is keyed by resolved absolute path.
  • signal — the turn's AbortSignal. bash passes it to Bun.spawn; grep passes it to the ripgrep spawn and checks it between files in the fallback scanner; read checks it up front (v0 reads a file in a single pass, so there are no chunk boundaries to poll). On abort, run() returns promptly (with error:"aborted") so the loop can unwind (loop invariants).
  • log — structured logging that also feeds the transcript. Tools open a scoped child (ctx.log.child("<tool>")) and log decisions (backend chosen, truncation applied) at debug; never log file contents or secrets.
Why a read-set, not mtime checks v0 deliberately tracks "did the model read this file this session" rather than detecting on-disk staleness. It is the cheap, deterministic prerequisite that makes edit safe to apply without a fuzzy matcher. Detecting external modification between read and edit is deferred (it belongs with the post-v0 diff review surface).

10 Shared mechanic — the exact-string edit algorithm

This is the precise procedure edit.run() executes. It is intentionally simple: read prerequisite, exactly-one-match, replace, write back. Any deviation returns ok:false with a specific, model-actionable error and leaves the file untouched.

Steps

  1. Resolve path against ctx.cwd and normalize to an absolute path p.
  2. Read-prerequisite check. If !ctx.readSet.has(p) → return ok:false, error:
    "must read <p> before editing it". No disk access beyond resolution.
  3. Load the current file bytes as UTF-8 (src). If the file is missing → ok:false, error: "file not found: <p>".
  4. Count matches of old_string in src as a literal substring (no regex):
    • 0 matches → ok:false, error: "old_string not found in <p> — it must match the file exactly, including whitespace".
    • >1 matches → ok:false, error: "old_string matched N times in <p> — add surrounding context so it is unique" (with the literal count).
    • exactly 1 → proceed.
  5. Replace the single occurrence: out = src.slice(0,i) + new_string + src.slice(i + old_string.length).
  6. Write back out to p (the file already exists, so no parent-dir creation). Honor ctx.signal.
  7. Return ok:true, content:"edited <rel> at line <L>" where L is the 1-based line of index i; meta = { path, line, removed, added } as in §7.

The old_string !== new_string guard is enforced by the schema's .refine() before run() is ever reached, so a no-op edit is rejected at validation time (§13), not inside the algorithm.

edit.run(input, ctx) ├─ p = resolve(cwd, path) ├─ readSet.has(p)? ── no ──> ok:false "must read <p> before editing it" ├─ src = read(p) ── missing ──> ok:false "file not found: <p>" ├─ n = count(src, old_string) │ n == 0 ──> ok:false "old_string not found … exactly, including whitespace" │ n > 1 ──> ok:false "old_string matched n times … add surrounding context" │ n == 1 ──> continue ├─ out = splice(src, i, old_string, new_string) ├─ write(p, out) └─ ok:true "edited <rel> at line L" meta:{path,line,removed,added}
Edit strategy — post-v0 v0 commits to exact-string replacement for its determinism and zero applier complexity. The longer-term path is unified-diff / patch application, landing with the deferred diff review UI (the diff format and the review surface are the same artifact). Line-range editing is rejected outright — line-number drift across multi-edit turns risks silent corruption. See v0 §7 and decisions.html.

11 Shared mechanic — output truncation policy

Tool output that flows back to the model is capped so a single read of a generated file or a noisy bash run cannot blow the context window. The policy is uniform and lives in one helper so every tool truncates identically.

Policy

  • Byte cap: MAX_TOOL_BYTES = 30_000 (~30 KB) of UTF-8 model-facing content. (Per-tool line/entry/match caps in §2–§8 apply before this and may cut sooner.)
  • Head + tail. When the cap is exceeded, keep the first ~20 KB and the last ~10 KB and drop the middle — the start (context, first errors) and end (final status, stack tail) are the most useful.
  • Notice. A single line marks the cut, with how much was removed.
  • meta.truncated = true whenever any cut occurred, so the TUI can badge the card and the transcript records it.
const MAX_TOOL_BYTES = 30_000;
const HEAD = 20_000;
const TAIL = 10_000;

function truncate(s: string): { content: string; truncated: boolean } {
  const bytes = Buffer.byteLength(s, "utf8");
  if (bytes <= MAX_TOOL_BYTES) return { content: s, truncated: false };
  const head = sliceBytes(s, 0, HEAD);
  const tail = sliceBytes(s, bytes - TAIL, bytes);
  const dropped = bytes - HEAD - TAIL;
  const notice = `\n\n… [truncated ${human(dropped)} of output] …\n\n`;
  return { content: head + notice + tail, truncated: true };
}

sliceBytes slices on UTF-8 byte offsets but snaps to the nearest codepoint boundary so the notice never splits a multibyte character. Tools call truncate() on their assembled content just before returning and set meta.truncated from its result (OR-ing with any earlier per-tool cap).

Live vs. model-facing Truncation applies only to the model-facing content. bash still streams the complete stdout/stderr to the TUI scrollback live, and the full output is what the user sees — the cap exists purely to bound context tokens.

12 Shared mechanic — grep ripgrep-with-fallback detection

grep prefers ripgrep (rg) for speed and gitignore-awareness, but must work on a machine without it. Detection happens once per session and is cached; the result is reported in meta.backend.

Detection

  1. On first grep call, probe for rg on PATH by spawning rg --version via Bun.spawn and checking for exit code 0.
  2. Cache the boolean on the registry (session-scoped) so subsequent calls skip the probe.
  3. If present → ripgrep backend: build rg --json (or line args) honoring ignoreCase (-i), context (-C), and glob (-g); parse output into the shared shape.
  4. If absent → fallback backend: a pure-Bun walk using Bun.Glob to enumerate files (respecting the glob arg), Bun.file().text() to read them, and the JS RegExp engine to match lines. Binary files are skipped via a NUL-byte sniff; the same caps from §5/§11 are enforced in-process.
let rgAvailable: boolean | null = null;   // session-cached

async function hasRipgrep(): Promise<boolean> {
  if (rgAvailable !== null) return rgAvailable;
  try {
    const p = Bun.spawn(["rg", "--version"], { stdout: "ignore", stderr: "ignore" });
    rgAvailable = (await p.exited) === 0;
  } catch {
    rgAvailable = false;   // ENOENT -> not on PATH
  }
  return rgAvailable;
}
Parity contract Both backends MUST produce the same ToolResult shape, the same path:line:text rendering, the same "no match = ok:true, empty" semantics, and obey the same caps. The only observable difference is meta.backend and the fallback's lack of native .gitignore filtering. Regex dialect differences (PCRE2 vs. JS) are a known fallback caveat noted to the user, not papered over.

13 Shared mechanic — the tool registry

The registry holds the registered Tool instances and is the single chokepoint between the model and tool execution. It does three jobs: emit the model-facing schemas, dispatch a validated call, and normalize every outcome into a ToolResult.

class ToolRegistry {
  private tools = new Map<string, Tool<unknown>>();

  register<I>(tool: Tool<I>): void { this.tools.set(tool.name, tool); }

  // (1) model-facing JSON Schema, one ToolSpec per tool
  specs(): ToolSpec[] {
    return [...this.tools.values()].map(t => ({
      name: t.name,
      description: t.description,
      schema: z.toJSONSchema(t.schema),   // zod 4 -> JSON Schema
    }));
  }

  // (2) validate -> (3) dispatch -> normalize
  async run(call: ToolCall, ctx: ToolContext): Promise<ToolResult> {
    const tool = this.tools.get(call.name);
    if (!tool) {
      return { ok: false, content: "", error: `unknown tool: ${call.name}` };
    }
    const parsed = tool.schema.safeParse(call.input);   // validate BEFORE run
    if (!parsed.success) {
      return {
        ok: false,
        content: "",
        error: `invalid input for ${call.name}: ${formatZodError(parsed.error)}`,
        meta: { validation: parsed.error.issues },
      };
    }
    try {
      return await tool.run(parsed.data, ctx);
    } catch (err) {
      ctx.logger.error("tool threw", { tool: call.name, err: String(err) });
      return { ok: false, content: "", error: normalizeError(err) };   // never throw
    }
  }
}

(1) specs() — model-facing schema

Each tool's zod schema is converted to JSON Schema via z.toJSONSchema (zod 4). The result is wrapped in a provider-neutral ToolSpec[]; the provider adapters map that to Anthropic input_schema or OpenAI tools[].function.parameters (the normalization map lives in v0 §6 and providers.html). The .describe() text on each field becomes the JSON Schema description, so the schemas above are the documentation the model reads.

(2) Validation before execution

schema.safeParse(call.input) runs before run(), before the permission gate. A validation failure short-circuits to an ok:false result whose error names the offending field — actionable for the model to retry — and never reaches disk or the approval prompt. Defaults declared in the schema (e.g. bash.timeout_ms, ls.all) are materialized here, so run() always receives a fully-populated, typed I.

(3) Error normalization

The registry guarantees the loop's "every call gets a result" invariant: run() may reject or throw, but the registry catches it and returns a ToolResult. normalizeError() maps common failures to clean, model-facing strings:

ThrownNormalized error
ENOENT"file not found: <path>"
EACCES / EPERM"permission denied: <path>"
EISDIR"path is a directory"
AbortError"aborted"
other Errorerr.message (one line, no stack)

Stack traces and raw errors go to ctx.logger / the transcript, never into model-facing content. A denied permission decision also returns a normalized ToolResult (ok:false, "denied by user") rather than throwing — see v0 §8. The net effect: the agent loop can always append a tool result and proceed, satisfying the loop invariants.

v0 scope Tools run sequentially in v0 (one call, one result, next call). Parallel tool calls are deferred (roadmap.html), so the registry needs no concurrency control beyond the per-turn AbortSignal.
