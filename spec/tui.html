TUI Layer

OpenTUI component spec — the terminal frontend that consumes the core's AgentEvent stream.

@opentui/core 0.3.0 Yoga flexbox Bun Draft · 2026-05-30

01 Role & Boundary

The TUI is the M5 frontend. It is a pure consumer of the core's AgentEvent async-iterable and a producer of two things back into the core: user messages and approval responses. It owns rendering state only — never session state.

This page elaborates §10 of the core spec against the real @opentui/core 0.3.0 surface. The seam this layer hangs off of is the AgentEvent union (defined in v0 §4); the TUI translates each event into a renderable mutation and nothing more.

  • No business logic. The TUI never decides whether a tool is allowed, never appends to Session.messages, never serializes a transcript. It renders what it is told and forwards what the user types.
  • Swappable. The TUI and the headless stdout frontend (§10) implement one Frontend interface, so main.ts picks one at boot. M1–M4 run headless; M5 swaps in the TUI.
  • Cancellation source. Ctrl-C in the TUI fires the AbortController whose signal threads through the provider stream and Bun.spawn (v0 §5 loop invariants).
Direction of data Core → TUI is events (read-only render instructions). TUI → Core is exactly two callbacks on the Frontend interface: onSubmit(text) and onApproval(id, decision). There is no third channel and no shared mutable state.

02 OpenTUI 0.3.0 API surface

v0 targets the verified @opentui/core 0.3.0 primitives. Layout is Yoga flexbox — every renderable takes flexbox-style props (flexDirection, flexGrow, gap, padding). The renderer is created asynchronously and renderables are composed into a tree under its root.

createCliRenderer()Async — must be awaited. Returns the renderer whose .root is the top-level container we parent regions under.
BoxRenderableThe structural primitive. Carries border, title, backgroundColor, flexDirection, gap, padding. Used for the root layout and for each tool card.
TextRenderableA run of text. The live assistant block is one of these, mutated on each text.delta.
StyledText / TextAttributescreateTextAttributes({ ... }) builds fg/bg/bold/dim attribute sets; StyledText wraps colored spans (tool-name green, edit-removed red, edit-added green).
InputRenderableThe prompt line: value, placeholder, onInput, onSubmit, focus() / blur(), programmatic submit().

const renderer = await createCliRenderer();   // async — note the await
const root = renderer.root;
Composition Renderables form a tree under renderer.root; children are attached via parent.add(child) (parenting). The TUI builds the four-region tree once at startup, then mutates child renderables in place as events arrive — it does not rebuild the tree per frame.

03 Layout & Regions

The screen is a single column (flexDirection: "column") of four regions. The header and input are fixed-height; the scrollback grows (flexGrow: 1) to fill the middle; the approval bar is zero-height until an approval.request arrives, then expands.

04 Component tree

The tree is built once in the TUI constructor. Region renderables are held as fields so events can mutate them directly. Tool cards are tracked in a Map<string, ToolCard> keyed by the tool.start id, so tool.result can find and update the right card.

class TuiFrontend implements Frontend {
  private renderer!: Awaited<ReturnType<typeof createCliRenderer>>;
  private header!: BoxRenderable;
  private scrollback!: ScrollBoxRenderable;
  private approvalBar!: BoxRenderable;
  private select!: SelectRenderable;
  private input!: InputRenderable;

  // live render state (NOT session state)
  private liveAssistant: TextRenderable | null = null;   // current text.delta target
  private toolCards = new Map<string, ToolCard>();        // tool.start id → card
  private pendingApproval: ((d: Decision) => void) | null = null;

  async mount(): Promise<void> {
    this.renderer = await createCliRenderer();
    const root = new BoxRenderable({ flexDirection: "column", flexGrow: 1 });

    this.header = new BoxRenderable({ height: 1, padding: { left: 1, right: 1 } });
    this.scrollback = new ScrollBoxRenderable({ flexGrow: 1 });
    this.approvalBar = new BoxRenderable({ visible: false, border: true,
                                           backgroundColor: "#1c2128" });
    this.select = new SelectRenderable({
      options: [
        { name: "Allow once",    value: "once" },
        { name: "Allow session", value: "session" },
        { name: "Deny",          value: "deny" },
      ],
    });
    this.input = new InputRenderable({ placeholder: "Ask om-cli…" });

    this.approvalBar.add(this.select);
    root.add(this.header);
    root.add(this.scrollback);
    root.add(this.approvalBar);
    root.add(this.input);
    this.renderer.root.add(root);

    this.input.focus();
    this.wireKeys();   // §08
  }
}

interface ToolCard { box: BoxRenderable; body: TextRenderable; spinner: TextRenderable; }
One live block at a time liveAssistant is the TextRenderable currently receiving deltas. It is created lazily on the first text.delta after a tool result or user message, and sealed (set to null) on text.done so the next text run starts a fresh block below any tool cards.

05 Event → render mutation map

The TUI drives a single for await over the core's event stream. Each AgentEvent variant maps to exactly one render mutation. No event mutates session state.

AgentEventRender mutation
text.delta {text}Append text to liveAssistant (creating it if null). No scroll thrash — content grows in place.
text.done {text}Seal the block: liveAssistant = null so the next text starts fresh.
tool.start {id,name,input}Create a tool-card BoxRenderable (title = name, body = preview(input)), show a spinner, store it in toolCards[id], append to scrollback.
tool.result {id,output}Look up toolCards[id], stop the spinner, replace body with the (truncated) output.content; border turns red if !output.ok.
approval.request {id,tool,preview}Show the approval bar with preview, focus the SelectRenderable, blur input. Resolve the pending decision on choice (§07).
turn.done {stopReason,usage}Update header usage, re-enable + refocus the input, clear any spinner state.
error {message,fatal}Append a red error block to scrollback. If fatal, also disable input and surface an exit hint.
 
async function consume(events: AsyncIterable<AgentEvent>, tui: TuiFrontend) {
  for await (const ev of events) {
    switch (ev.type) {
      case "text.delta":
        tui.appendAssistant(ev.text);            // grows liveAssistant
        break;
      case "text.done":
        tui.sealAssistant();                     // liveAssistant = null
        break;
      case "tool.start":
        tui.openToolCard(ev.id, ev.name, ev.input);   // box + spinner
        break;
      case "tool.result":
        tui.closeToolCard(ev.id, ev.output);     // update card in place
        break;
      case "approval.request":
        await tui.askApproval(ev.id, ev.tool, ev.preview);  // §07
        break;
      case "turn.done":
        tui.setUsage(ev.usage);
        tui.enableInput();                       // refocus prompt
        break;
      case "error":
        tui.appendError(ev.message, ev.fatal);
        break;
    }
  }
}

Tool card lifecycle

openToolCard(id: string, name: string, input: unknown) {
  const box = new BoxRenderable({ border: true, title: name,
                                  flexDirection: "column", padding: 1 });
  const spinner = new TextRenderable({ content: "⠋ running…",
                                       attributes: createTextAttributes({ dim: true }) });
  const body = new TextRenderable({ content: this.previewFor(name, input) });
  box.add(body); box.add(spinner);
  this.scrollback.add(box);
  this.toolCards.set(id, { box, body, spinner });
}

closeToolCard(id: string, output: ToolResult) {
  const card = this.toolCards.get(id);
  if (!card) return;
  card.spinner.visible = false;                  // stop spinner
  card.body.content = truncateForCard(output.content);
  if (!output.ok) card.box.borderColor = "#ff7b72";   // --red on failure
  this.toolCards.delete(id);
}
bash streaming Per v0 §7, the bash tool tails stdout/stderr live. While its card is open, incremental output appends to card.body exactly like text.delta appends to the assistant block, until tool.result seals the final content.

06 Input → core message flow

On onSubmit, the input's value is handed to the core via the onSubmit(text) Frontend callback and the input is cleared and blurred for the duration of the turn. The TUI does not append the user message to the session — the core does that, then begins streaming events the TUI renders. This keeps the canonical message store the single source of truth.

InputRenderable.onSubmit(text) │ ▼ frontend.onSubmit(text) ─────────▶ Core: session.append(user, text) │ (input cleared, blurred) │ │ ▼ │ runTurn(session) ──▶ AsyncIterable<AgentEvent> ▼ │ render echo of user line ▼ into scrollback (cosmetic) for await (ev of events) → render
// in mount(), after constructing this.input:
this.input.onSubmit = (text: string) => {
  const trimmed = text.trim();
  if (!trimmed) return;
  this.echoUser(trimmed);          // cosmetic scrollback line, NOT session state
  this.input.value = "";
  this.input.blur();               // locked while the turn runs
  this.onSubmit?.(trimmed);        // hand to core via the Frontend callback
};
Echo is cosmetic The user line rendered on submit is a render convenience so the prompt doesn't vanish before the assistant replies. It is independent of the canonical message the core appends. If they ever disagree, the core's store wins (v0 source-of-truth rule).

07 Approval-response → core flow

On approval.request, the loop is blocked in the permission gate waiting for a Decision. The TUI shows the approval bar and resolves a promise when the user chooses. The TUI maps the UI choice to the core's Decision shape and sends it back — it never decides anything itself, and a deny still flows back so the core can return a tool result.

askApproval(id: string, tool: string, preview: string): Promise<void> {
  this.approvalBar.title = `Allow ${tool}?`;
  this.setApprovalPreview(preview);
  this.approvalBar.visible = true;
  this.input.blur();
  this.select.focus();

  return new Promise<void>((resolve) => {
    const finish = (decision: Decision) => {
      this.approvalBar.visible = false;
      this.select.blur();
      this.onApproval?.(id, decision);   // → core gate
      resolve();
    };
    this.select.onSelect = (value: "once" | "session" | "deny") => {
      finish(toDecision(value));
    };
    this.pendingApproval = finish;   // so y/a/n keys can resolve it too (§08)
  });
}

// UI choice → canonical Decision (v0 §8)
function toDecision(v: "once" | "session" | "deny"): Decision {
  if (v === "deny")    return { allowed: false, reason: "denied by user" };
  if (v === "session") return { allowed: true, remember: "session" };
  return { allowed: true };                    // allow once
}

The three options map directly to the v0 §8 approval modal: Allow once → {allowed:true}, Allow session → {allowed:true, remember:"session"} (the gate then adds a tool+arg-signature entry to the session allowlist), Deny → {allowed:false, reason}. On deny the core still returns a tool result ("denied") so every call gets a result (loop invariant, v0 §5).

08 Keybindings

A single KeyHandler intercepts control keys globally; context decides what fires. Plain typing flows to the focused InputRenderable untouched.

KeyContextAction
EnterInput focusedSubmit (InputRenderable.onSubmit) → frontend.onSubmit(text).
Ctrl-CTurn activeFire the current turn's AbortController.abort(); the signal unwinds the provider stream + Bun.spawn.
Ctrl-CIdle (no active turn)Clear the input line; a second press exits (mirrors common shell behavior).
Ctrl-DEmpty inputExit: frontend.dispose() then process exit.
yApproval shownAllow once → resolve pending decision.
aApproval shownAllow session → resolve pending decision.
nApproval shownDeny → resolve pending decision.
 
wireKeys() {
  this.renderer.keyHandler.on("keypress", (ev: KeyEvent) => {
    // approval has priority: y/a/n resolve the blocked gate
    if (this.pendingApproval) {
      if (ev.name === "y") return this.pendingApproval(toDecision("once"));
      if (ev.name === "a") return this.pendingApproval(toDecision("session"));
      if (ev.name === "n") return this.pendingApproval(toDecision("deny"));
    }
    if (ev.ctrl && ev.name === "c") {
      if (this.activeAbort) this.activeAbort.abort();   // interrupt the turn
      else this.input.value = "";                        // idle: clear line
      return;
    }
    if (ev.ctrl && ev.name === "d" && this.input.value === "") {
      this.dispose();                                     // Ctrl-D exit
      process.exit(0);
    }
  });
}
Abort ownership The TUI holds the AbortController for the in-flight turn and passes its signal into the core when calling submit. On abort the core emits a synthetic interrupted tool result and a turn.done; the TUI then re-enables input as usual. The TUI never tears down state on its own — it waits for turn.done.

09 The shared Frontend interface

Both frontends — the OpenTUI TuiFrontend and the headless StdoutFrontend — implement one interface so main.ts can choose at boot without the core knowing which is live. The core depends only on this interface, not on OpenTUI.

interface Frontend {
  /** Prepare the frontend (TUI: await createCliRenderer; stdout: no-op). */
  mount(): Promise<void>;

  /** Render a stream of core events to completion (one turn). */
  render(events: AsyncIterable<AgentEvent>): Promise<void>;

  /** Core → frontend: register the callbacks the frontend invokes. */
  onSubmit?: (text: string, signal: AbortSignal) => void;
  onApproval?: (id: string, decision: Decision) => void;

  /** Tear down (TUI: restore terminal; stdout: flush). */
  dispose(): Promise<void>;
}

The wiring in main.ts stays frontend-agnostic. The driver loop reads user input from the frontend, asks the core for an event stream, and hands it back to the frontend to render:

// main.ts — picks a frontend, never imports OpenTUI types directly
const frontend: Frontend = useTui ? new TuiFrontend() : new StdoutFrontend();
await frontend.mount();

frontend.onSubmit = async (text, signal) => {
  session.append({ role: "user", content: text });   // core owns the store
  await frontend.render(runTurn(session, { signal })); // §05 consumer
};
frontend.onApproval = (id, decision) => gate.resolve(id, decision);
Why one interface Keeping Frontend tiny is what lets v0 build the loop headless (M1–M4) and swap in the TUI at M5 (milestones, v0 §12) without touching the core or providers.

10 Headless stdout fallback

The headless frontend is the M1–M4 frontend and the permanent debug/CI path. It implements the same Frontend interface using only process.stdout / process.stdin — no OpenTUI, no alt-screen — so the agent loop, providers, tools, and permission gate can be proven before any terminal rendering exists.

class StdoutFrontend implements Frontend {
  onSubmit?: (text: string, signal: AbortSignal) => void;
  onApproval?: (id: string, decision: Decision) => void;

  async mount() {
    process.stdin.setRawMode?.(false);
    this.prompt();                                  // print "> "
    for await (const line of console) {             // Bun line reader
      const ctrl = new AbortController();
      this.onSubmit?.(line.trim(), ctrl.signal);
    }
  }

  async render(events: AsyncIterable<AgentEvent>) {
    for await (const ev of events) {
      switch (ev.type) {
        case "text.delta":  process.stdout.write(ev.text); break;
        case "text.done":   process.stdout.write("\n"); break;
        case "tool.start":  console.log(`\n[tool] ${ev.name} ${JSON.stringify(ev.input)}`); break;
        case "tool.result": console.log(`[result] ${ev.output.ok ? "ok" : "ERR"}: ` +
                                        truncate(ev.output.content)); break;
        case "approval.request": {
          // synchronous prompt on stdin: y / a / n
          const ans = await this.readKey(`Allow ${ev.tool}? [y/a/n] `);
          this.onApproval?.(ev.id, toDecision(
            ans === "a" ? "session" : ans === "y" ? "once" : "deny"));
          break;
        }
        case "turn.done":   console.log(`\n[done] ${ev.stopReason}  ` +
                                        `${ev.usage.input}/${ev.usage.output} tok`); break;
        case "error":       console.error(`[error] ${ev.message}`); break;
      }
    }
    this.prompt();
  }

  async dispose() { /* nothing to restore */ }
}

The two frontends share toDecision() and truncate() helpers and render the identical event set — they differ only in how they paint it. That symmetry is the test: if a turn behaves correctly under StdoutFrontend, the TUI is purely a rendering concern on top.

11 Open question — scrollback performance

Open · validate at M5 Carried from v0 §13: does OpenTUI's reactivity handle a long, continuously mutating scrollback efficiently, or do we need windowed rendering early? A long coding session can accumulate hundreds of text blocks and tool cards under one ScrollBoxRenderable.

The plan is to build M5 against the naive "append every block as a child" model and measure. If frame cost grows with total scrollback size rather than visible viewport, we fall back to windowing:

  • Virtualize the viewport. Keep the full conversation in a plain in-memory array of render descriptors; only mount the BoxRenderable/TextRenderable children that fall in (or near) the visible scroll window, mounting/unmounting as the user scrolls.
  • Cap mounted tool cards. Collapse older completed tool cards to a one-line summary renderable; expand on demand.
  • Coalesce deltas. Batch rapid text.delta appends within a frame instead of mutating the live block per token, to bound re-layout cost.

Windowing is a fallback, not a v0 commitment — it lands only if measurement at M5 shows the naive model degrades. The Frontend interface and the event→mutation map (§05) are unaffected either way; windowing is internal to TuiFrontend.
