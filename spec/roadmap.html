Post-v0 Roadmap

What we deliberately cut from v0, why, and the rough order it comes back. Each item is a spec sketch, not a commitment — phases shift as v0 ships.

v0.x · incremental v1 · larger surface design reference

00How to read this

v0 (defined in v0.html) is the buildable core: a single Bun process, a UI-agnostic Core emitting a typed AgentEvent stream, two providers behind one Provider interface, seven tools, three permission classes, and append-only JSONL transcripts. Everything below was cut from that line deliberately to keep v0 shippable. Nothing here overrides a v0 decision; it elaborates on what comes after.

Each feature carries a phase badge and a short dependency note. Phases are coarse:

  • v0.x  Incremental additions that fit the existing architecture with little structural change — mostly new tools, new event shapes, or config keys.
  • v1  Larger surface changes that touch the agent loop, message store, or the provider layer in ways the v0 spec did not design for. These graduate the core spec to v1.html.
Consistency rule Anything here that contradicts v0.html is a bug in this page. Where a v0 "Open Question" is resolved post-v0 (e.g. Responses store:false statefulness, OpenTUI scrollback), the resolution is tracked in decisions.html, not here.

02Wave 1 — v0.x (incremental)

These slot into the v0 architecture without graduating the core spec. They add tools, event variants, and config keys; they do not rewrite the loop or the message store.

Parallel tool calls (within one turn)

v0.x

v0 executes tool calls sequentially (Loop invariant: "sequential tools in v0"). A single assistant turn can emit several tool_call items; v0.x runs the independent ones concurrently and still emits exactly one tool.result per call.

Spec sketch

The loop already collects all tool calls from a turn before dispatching. Replace the serial for loop with a bounded concurrent map. Each tool keeps its existing permission class; approval prompts are resolved before any execution begins, so the user is never racing modals. write/edit on the same path stay serialized by a per-path lock to preserve the must-have-read + unique-match guarantees.

// loop.ts — replaces the sequential dispatch
const calls = turn.toolCalls;                 // ToolCall[]
const decisions = await resolveApprovals(calls, session.allowlist); // all modals first
const results = await mapConcurrent(calls, MAX_PARALLEL_TOOLS, (call) =>
  decisions[call.id].allowed
    ? withPathLock(call, () => runTool(call, ctx))
    : deniedResult(call, decisions[call.id].reason),  // deny still returns a result
);
for (const r of results) session.appendToolResult(r);  // ordered by call index

Tool result ordering in the message store stays deterministic (by original call index) so transcripts replay identically regardless of finish order. AbortSignal still unwinds every in-flight tool cleanly — the existing invariant just fans out.

Why deferred v0 wanted one provably-correct path through the loop. Concurrency interacts with the approval modal, the per-path edit invariants, and abort unwinding — each a place to introduce a race. Sequential-first makes those invariants trivially true; parallelism is a measured optimization on top.
Depends on: nothing. Unlocks: sub-agent fan-out (which is parallel tool calls one level up). See the loop spec in v0 §Agent Loop and tools.html.

Session resume from JSONL

v0.x

v0 writes an append-only transcript to .om/transcripts/<session-id>.jsonl but never reads it back. Resume reconstructs a live Session from that file so a crashed or closed session can continue.

Spec sketch

The transcript is the source of truth — replay it to rebuild messages, usage, and the resolved systemPrompt. The session allowlist is not restored (it is explicitly session-scoped in v0); the user re-approves write/exec on first use after resume. Because OpenAI runs with store:false and we own all state, replay is symmetric across both providers — we just re-send the full history, exactly as v0 already does each turn.

async function resume(sessionId: string): Promise<Session> {
  const lines = (await Bun.file(transcriptPath(sessionId)).text())
    .split("\n").filter(Boolean).map((l) => JSON.parse(l) as TranscriptEntry);
  const s = new Session(sessionId);
  for (const e of lines) {
    if (e.kind === "message") s.messages.push(e.message);
    if (e.kind === "tool_result") s.appendToolResult(e.result);
    if (e.kind === "usage") s.usage = e.usage;       // last one wins
  }
  s.systemPrompt = reassembleSystemPrompt();          // re-run env/OM.md assembly
  s.allowlist = new Set();                            // intentionally fresh
  return s;
}

CLI surface: om --resume <session-id> and a "most recent" shorthand om --continue. A schema-version field on each transcript entry lets us refuse or migrate older formats rather than mis-parsing them.

Why deferred v0 explicitly has "no compaction" and a fixed system-prompt assembly order; resume only needs the transcript format to be stable first. It was cut to avoid pinning the JSONL schema before the tools that write it settled.
Depends on: stable transcript schema (v0 §Sessions). Unlocks: compaction and cross-session memory.

Diff review UI / patch staging

v0.x

v0 ships two write tools: write (full file) and edit (exact-string, unique-match, must-have-read). v0 deliberately deferred unified-diff edits — and this is where that strategy lands. The diff UI is the natural home for it because a hunk-based edit is only safe to apply if the user can review the rendered patch first.

Spec sketch

Add a third write tool, apply_patch, taking a unified diff. Its preview(input) returns the rendered hunks; the TUI shows a colorized diff card (green adds / red removes) in place of the plain approval modal. The user can Allow once, Allow session, or Deny — the same decision vocabulary as v0's permission gate, just with a richer preview. Multiple pending edits stage into a review queue applied atomically on accept.

const applyPatch: Tool<{ patch: string }> = {
  name: "apply_patch",
  description: "Apply a unified diff. Each hunk must apply cleanly against the file as read this session.",
  schema: z.object({ patch: z.string() }),
  permission: "write",                       // same gate as write/edit
  preview: (i) => renderHunks(i.patch),       // drives the diff card, not a one-line string
  run: async ({ patch }, ctx) => {
    const hunks = parseUnifiedDiff(patch);
    for (const h of hunks) requireReadThisSession(ctx, h.path);  // v0's must-have-read carries over
    return applyAtomically(hunks);           // all-or-nothing; ToolResult on failure
  },
};

The existing preview(input): string tool contract widens to allow a structured preview the TUI can render as a diff; string previews stay valid for every other tool. edit and write are unchanged.

Why deferred Per v0 "Decided: exact-string edit (diff post-v0)". Unified-diff parsing/fuzzing and a diff-rendering TUI component are both real surface area; exact-string editing covers the common case with far less ambiguity, so the diff path waits for its review UI.
Depends on: the OpenTUI shell (v0 M5) and the preview contract. Unlocks: safer multi-file refactors. See tools.html (edit algorithm) and tui.html.

Hooks & lifecycle events

v0.x

Let users run shell commands at well-defined points in the agent lifecycle — e.g. run a formatter after every write, or block a bash call by policy. Hooks are configured, not coded, and observe (or veto) the existing AgentEvent stream.

Spec sketch

The Core already emits a typed event stream. Hooks tap named lifecycle points that map onto those events. A hook is a shell command receiving JSON on stdin; a non-zero exit on a pre hook turns into a denial (which, per v0, still returns a tool result to the model).

Hook pointFires onCan veto?
session.startsession created / resumedno
user.promptbefore a user turn is sentno
tool.prebefore a tool runs (after approval)yes → denial
tool.postafter tool.resultno
turn.doneon the turn.done eventno
 
// ~/.om/config.json  (merged with project ./.om/config.json per v0 order)
{
  "hooks": {
    "tool.post": [
      { "match": { "name": "write|edit|apply_patch" }, "run": "bunx prettier --write $OM_TOOL_PATH" }
    ],
    "tool.pre": [
      { "match": { "name": "bash" }, "run": ".om/guard-bash.sh" }   // exit!=0 ⇒ deny
    ]
  }
}
Why deferred Hooks are a public extension contract — once people script against the event names and stdin JSON, those become an API. v0 fixes the AgentEvent union first so the hook points can map onto it without churn.
Depends on: the stable AgentEvent union and the permission gate (v0 §Permissions). Pairs with: slash-commands (shared config surface).

Slash-commands & skill system

v0.x

Two related ideas. Slash-commands are user-invoked prompt templates (/review, /test) expanded inline before a turn. Skills are reusable instruction bundles (a markdown body, optional allowed-tools list) the model can load on demand to specialize behavior without bloating the base system prompt.

Spec sketch

Slash-commands are pure client-side: a command file is markdown with frontmatter, and invoking /name args substitutes $ARGUMENTS and runs it as the user turn. No loop changes. Skills layer onto v0's system-prompt assembly: the base order is base → env block → project OM.md → tool usage notes; an activated skill's body is appended as an additional block, never reordering the existing four.

// .om/commands/review.md
---
description: Review the current diff for bugs
allowed-tools: [read, grep, glob]      # optional narrowing for this command's turn
---
Review the staged changes for correctness and clarity. Focus on $ARGUMENTS.
// resolved at invocation
expandSlash("/review error handling")
  => userMessage(body.replace("$ARGUMENTS", "error handling"));

Discovery follows v0's config precedence: ~/.om/commands/ then ./.om/commands/, project overriding user. Skills live alongside under commands/'s sibling skills/ and are surfaced to the model as a lightweight index it can choose to expand.

Why deferred Not needed to prove the loop. It is pure ergonomics built on the v0 system-prompt assembly and config-merge order, both of which must be fixed first so command/skill discovery has a stable precedence to inherit.
Depends on: system-prompt assembly + config merge order (v0 §Config). Unlocks: a clean home for memory recall commands.

03Wave 2 — v1 (structural)

These reshape the core enough to graduate the spec to v1.html. Each builds on one or more v0.x items above.

MCP client / external tool servers

v1

Connect to Model Context Protocol servers and expose their tools to the agent as if they were native. This makes om-cli extensible without recompiling — the killer feature for third-party tools.

Spec sketch

An MCP client connects to configured servers (stdio or HTTP) and lists their tools. Each remote tool is wrapped in an adapter that satisfies v0's Tool<I> interface: the server's JSON Schema becomes the tool schema (round-tripped through zod so validation stays uniform), and run forwards arguments over the protocol. Every MCP tool gets a permission class — defaulting to the most restrictive (exec, i.e. prompt) — and flows through the same approval gate as native tools. The model never sees a difference; the registry just has more entries.

function mcpTool(server: McpConn, def: McpToolDef): Tool<unknown> {
  return {
    name: `${server.alias}__${def.name}`,        // namespaced to avoid collisions
    description: def.description,
    schema: jsonSchemaToZod(def.inputSchema),     // uniform validation
    permission: server.config.permission ?? "exec",  // restrictive default; gate is unchanged
    preview: (i) => `${server.alias}: ${def.name}(${summarize(i)})`,
    run: (i, ctx) => server.call(def.name, i, ctx.signal),  // AbortSignal threaded through
  };
}
Why deferred It widens the trust boundary: tools now execute outside our process. v0's permission model (auto-allow read / prompt write+exec, session allowlist keyed by tool+arg-signature) is the prerequisite — MCP tools must inherit it exactly, with no project-root jail and deny-still-returns-a-result preserved.
Depends on: tool registry + permission gate (v0 §Permissions), zod schema plumbing. Pairs with: hooks for policy on remote tools.

Context compaction / summarization

v1

v0 states "No compaction in v0" — history grows unbounded until the turn cap or the context window stops it. v1 compacts old turns into a summary when the window approaches its limit, so long sessions keep working.

Spec sketch

Watch token usage (already tracked on the session and emitted on turn.done). When it crosses a threshold, take a prefix of older messages, ask the model to summarize them, and replace that prefix with a single synthetic summary message — keeping recent turns and any pinned context verbatim. The full untouched history still lives in the JSONL transcript, so compaction never loses data; it only shrinks the in-context window.

before [sys][m1][m2][m3]...[m40][m41] ← near window limit after [sys][summary of m1..m32][m33]...[m41] transcript.jsonl still holds m1..m41 verbatim (append-only, untouched)

Symmetric across providers: both already resend full history every turn, so compaction is purely a transform on our canonical Message[] before serialization — no per-provider special-casing. A compaction event is emitted so the TUI can show a "history summarized" marker.

Why deferred Summarization is lossy and easy to get subtly wrong (dropping a decision the model later needs). v0 keeps history honest and bounded by the max-iteration turn cap instead. Compaction wants resume's replay logic and a settled transcript schema first.
Depends on: session resume + transcript schema. Unlocks: long-lived sub-agents.

Sub-agents & parallel task fan-out

v1

A task tool that spawns a child agent loop with its own message store, runs it to completion on a scoped instruction, and returns its final answer as a single ToolResult. The parent fans several of these out at once for independent investigations.

Spec sketch

The agent loop is already UI-agnostic and emits an AgentEvent async-iterable. A sub-agent is just another instance of that loop — given a fresh Session, a restricted tool set, and a budget (its own turn cap). Its events are tagged with the child id so the TUI can nest them; only its turn.done text bubbles up to the parent as the tool output. Fan-out reuses parallel tool calls: spawning N task calls in one turn runs N child loops concurrently.

const task: Tool<{ prompt: string; tools?: string[] }> = {
  name: "task",
  description: "Delegate a scoped sub-task to a child agent. Returns its final report.",
  schema: z.object({ prompt: z.string(), tools: z.array(z.string()).optional() }),
  permission: "read",                          // spawning is safe; the child's own tools gate themselves
  preview: (i) => `delegate: ${i.prompt.slice(0, 60)}…`,
  run: async (i, ctx) => {
    const child = newSession({ tools: subsetTools(i.tools), turnCap: ctx.childCap });
    const final = await runLoop(child, i.prompt, ctx.signal);  // child events tagged + nested in TUI
    return { ok: true, content: final.text };
  },
};

Child tool calls still hit the parent's permission gate — delegation does not bypass approvals. Aborting the parent cancels all children via the shared AbortSignal tree.

Why deferred It is concurrency, budgeting, and nested-UI all at once. v0 proves a single loop end-to-end; sub-agents are that loop composed with itself, which is only sane once parallel dispatch and compaction (for long children) exist.
Depends on: parallel tool calls + compaction. Unlocks: per-task routing.

Multi-provider routing per task

v1

v0 picks one provider + model per session via config. v1 lets a request choose its provider/model — e.g. a cheap fast model for a task sub-agent, a strong model for the main thread.

Spec sketch

The Provider interface ({ id, stream(req) }) is already the only thing the loop talks to. Routing adds a thin resolver that maps a route key to a concrete provider instance + model, evaluated per ProviderRequest rather than once per session. Because the message store is canonical and per-provider adapters serialize on the way out, switching providers mid-session is just choosing a different adapter for the next request — the normalization map in providers.html already covers both wire formats.

type Route = { provider: "anthropic" | "openai"; model: string };
function resolveRoute(ctx: { role: "main" | "subagent"; hint?: string }): Route {
  return config.routes[ctx.role] ?? config.routes.default;   // config-driven, per request
}
// loop picks the adapter at send time:
const route = resolveRoute(ctx);
const provider = providers[route.provider];
yield* provider.stream({ ...req, model: route.model });
Why deferred Most useful once sub-agents exist (so there are distinct roles to route). v0 keeps a single provider/model to keep the cost/usage accounting and the Anthropic↔OpenAI normalization (still being proven) simple.
Depends on: the Provider interface (v0 §Provider Layer) + sub-agents. See: providers.html.

Persistent cross-session memory

v1

Durable facts that outlive a single session — "this repo uses pnpm", "the user prefers terse diffs" — recalled into future sessions without re-deriving them. v0's only persistence is the per-session JSONL transcript; memory is the first state shared across sessions.

Spec sketch

A memory store at ~/.om/memory/ (global) and ./.om/memory/ (project), following v0's config precedence. Reads fold into system-prompt assembly as a new block after project OM.md and before tool usage notes — extending the v0 order, not reordering it. Writes go through tools (memory_write / memory_forget) so they pass the permission gate and land in the transcript like any other effect — no silent background writes.

// system prompt assembly (v0 order, with the new block slotted in):
//   base → env block → project OM.md → [MEMORY block] → tool usage notes
const memory: Tool<{ key: string; value: string; scope: "project" | "global" }> = {
  name: "memory_write",
  description: "Persist a durable fact for future sessions.",
  schema: z.object({ key: z.string(), value: z.string(), scope: z.enum(["project", "global"]) }),
  permission: "write",                          // user-visible, gated, logged
  preview: (i) => `remember [${i.scope}] ${i.key} = ${i.value}`,
  run: (i) => writeMemory(i.scope, i.key, i.value),
};
Why deferred Cross-session state is a new durability and trust surface (stale facts, leaking project context into global scope). v0 stays strictly session-scoped — even the permission allowlist resets per session. Memory waits for resume and the skill/command machinery that gives it natural recall ergonomics.
Depends on: resume, system-prompt assembly, config precedence. Pairs with: slash-commands & skills.

04Still out of scope (for now)

Things explicitly not on this roadmap yet — listed so they are not mistaken for omissions:

  • A non-terminal UI (web / editor extension). The Core is UI-agnostic by design, so a second consumer is possible, but the TUI is the only planned front end.
  • A plugin/extension API beyond MCP and hooks — those two are the sanctioned extension surfaces.
  • Project-root path jail / sandboxing. v0 decided the approval prompt is the boundary; revisiting that is a decision, not a feature.
  • Provider-side state (OpenAI store:true, server-held threads). v0 owns all state with store:false; flipping this is an open question, tracked in decisions.html.
  • Fine-grained per-argument permissions beyond the v0 tool+arg-signature allowlist.
Where decisions live This page tracks what and roughly when. The why we chose X over Y for any of the above belongs in decisions.html (ADR-style), and the buildable contract for each shipped feature graduates into the core spec (becoming v1.html when the v1 wave lands).
