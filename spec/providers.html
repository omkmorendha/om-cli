Provider Layer

Deep dive — the Anthropic / OpenAI adapters that normalize two wire formats into one internal contract.

@anthropic-ai/sdk openai (Responses) zod 4 · z.toJSONSchema Draft · 2026-05-30

01 Role of the Layer

This page expands v0 §6. The provider layer is the single seam where the two model vendors enter the harness, and the only place in the codebase allowed to know SDK-specific shapes. Everything above it — the agent loop (§5), the session store (§9), the TUI — speaks only the canonical internal types.

An adapter does exactly two jobs, and nothing else:

  • Serialize on send. Take a ProviderRequest built from canonical Message[] + ToolSpec[] and shape it into that vendor's request body.
  • Parse on receive. Consume the vendor's streaming event sequence and emit a flat, vendor-neutral ProviderEvent stream.

No business logic lives here: adapters do not decide permissions, do not run tools, do not write transcripts. They are pure translators. That constraint is what keeps the loop provider-agnostic and what makes "switch providers mid-session" theoretically sound — the canonical store is authoritative, and either adapter can re-serialize the same history.

Agent Loop (§5) │ ProviderRequest{ system, messages[], tools[], signal } ▼ ┌─────────────────────────────────────────────┐ │ Provider (adapter) │ │ │ │ serialize ──▶ vendor wire body ──▶ SDK.stream │ │ │ │ ProviderEvent ◀── parse ◀── vendor stream │ └─────────────────────────────────────────────┘ │ text.delta · tool_call · done ▼ Agent Loop ──▶ AgentEvent to TUI
Boundary rule We never persist provider-native messages. The Session holds canonical Message[]; the adapter rebuilds the wire body from scratch on every turn. This is also why both providers resend full history (§5, §6).

02 Canonical Message & ToolCall

The internal message store is the source of truth referenced throughout v0 §9. It exists so the loop and session never have to branch on which provider is active — there is exactly one message shape, and adapters map both directions.

Why a canonical shape at all

  • One loop, two vendors. Without a canonical type the loop would carry if (provider === "anthropic") branches through every append and replay path. The type pushes all that branching into two small, testable files.
  • Lossless re-serialization. The store keeps enough structure (tool-use ids, tool results, text segments) that either adapter can reconstruct a valid request body — including the rule that every tool call must be echoed back with a matching result (§5 invariant).
  • Transcript fidelity. The JSONL transcript at .om/transcripts/<id>.jsonl serializes these canonical types directly — replaying it rebuilds messages with no vendor coupling.
// The canonical message store. Provider-neutral by construction.
type Role = "user" | "assistant";

interface Message {
  role: Role;
  content: ContentBlock[];   // ordered; mirrors the assistant's emission order
}

// Content is a small discriminated union — the common subset of both wire formats.
type ContentBlock =
  | { type: "text";        text: string }
  | { type: "tool_call";   call: ToolCall }                 // assistant asked for a tool
  | { type: "tool_result"; id: string; result: ToolResult } // our reply to that call

// A normalized tool invocation. `id` is the correlation key both APIs require:
// Anthropic's tool_use.id, OpenAI's function_call.call_id — stored as one field.
interface ToolCall {
  id: string;        // correlation id, round-tripped to the result
  name: string;      // tool name, must match a registered Tool (§7)
  input: unknown;    // parsed JSON arguments; validated by the tool's zod schema
}

Note that ToolResult is the same { ok, content, error?, meta? } shape defined in v0 §7 / detailed in tools.html — the provider layer reuses it verbatim, it does not define its own. The StopReason and Usage types are shared with the AgentEvent contract in §4:

type StopReason =
  | "end"          // model finished its turn, no tool requested
  | "tool_use"     // model is requesting one or more tools
  | "max_tokens"   // output length cap hit
  | "interrupted"  // AbortSignal fired mid-stream (§7)
  | "error";       // provider/stream error

interface Usage { inputTokens: number; outputTokens: number;
                  cacheReadTokens?: number; cacheWriteTokens?: number; }
Why input: unknown Arguments arrive as a JSON string fragment-stream from both vendors. The adapter accumulates and JSON.parses them but does not validate — validation is the tool's job via its zod schema at run time (§7). Keeping unknown here means the provider layer never needs to import a tool's schema.

03 Provider Contract & Lifecycle

The interface is unchanged from v0 §6 — reproduced here as the contract this page implements:

interface Provider {
  readonly id: "anthropic" | "openai";
  stream(req: ProviderRequest): AsyncIterable<ProviderEvent>;
}

interface ProviderRequest {
  system: string;
  messages: Message[];        // canonical (§2)
  tools: ToolSpec[];          // canonical; adapter translates per vendor
  signal: AbortSignal;        // threaded into the SDK call (§7)
}

type ProviderEvent =
  | { type: "text.delta"; text: string }
  | { type: "tool_call";  call: ToolCall }
  | { type: "done";       stopReason: StopReason; usage: Usage };

ToolSpec — the canonical tool descriptor

The loop passes registry.specs() (see tools.html): the model-facing slice of each Tool. The JSON Schema is produced once via z.toJSONSchema and is identical for both vendors — only the envelope around it differs (§4, §5).

interface ToolSpec {
  name: string;
  description: string;
  parameters: JSONSchema;     // z.toJSONSchema(tool.schema), computed once
}

Lifecycle of one stream() call

One call corresponds to exactly one provider turn (one iteration of the loop in §5). The contract:

  1. Serialize. Build the vendor request body from req. System prompt, history, and tools are all derived fresh from the canonical input.
  2. Open the SDK stream with req.signal attached.
  3. Emit deltas as they arrive. text.delta for prose, accumulate tool-call argument fragments internally.
  4. Emit each completed tool_call once its arguments JSON is fully buffered and parsed.
  5. Emit exactly one terminal done with the normalized stopReason and usage, then the iterator completes.
Invariants the adapter must uphold Exactly one done per stream, always last. A tool_call is emitted only after its full argument JSON is parsed (never partial). On abort the stream stops promptly and surfaces as described in §7. The adapter never emits approval.request or tool.result — those are loop/TUI concerns (§4).

04 Anthropic Messages Adapter

Backed by @anthropic-ai/sdk (Messages API) with streaming tool use. Anthropic models content as an ordered array of blocks per message, and tool calls are tool_use blocks inline in the assistant message.

Request shaping

The system prompt becomes the top-level system field, canonical messages become Anthropic messages[], and tools carry their JSON Schema under input_schema.

import Anthropic from "@anthropic-ai/sdk";

function toAnthropicTools(tools: ToolSpec[]): Anthropic.Tool[] {
  return tools.map((t) => ({
    name: t.name,
    description: t.description,
    input_schema: t.parameters,        // z.toJSONSchema output goes here directly
  }));
}

function toAnthropicMessages(messages: Message[]): Anthropic.MessageParam[] {
  return messages.map((m) => ({
    role: m.role,
    content: m.content.map((b) => {
      switch (b.type) {
        case "text":
          return { type: "text", text: b.text };
        case "tool_call":     // assistant block
          return { type: "tool_use", id: b.call.id,
                   name: b.call.name, input: b.call.input };
        case "tool_result":   // sent back inside a *user* message
          return { type: "tool_result", tool_use_id: b.id,
                   content: renderToolResult(b.result),
                   is_error: !b.result.ok };
      }
    }),
  }));
}

function buildAnthropicRequest(req: ProviderRequest, model: string) {
  return {
    model,
    max_tokens: 8192,
    system: req.system,                       // top-level system field
    messages: toAnthropicMessages(req.messages),
    tools: toAnthropicTools(req.tools),
    stream: true as const,
  };
}

tool_result placement. Anthropic requires tool results to be sent in a user-role message on the turn after the tool_use (this is the "tool_result echo on the next turn" from §6). Because the canonical store records each result as a tool_result block (§2), the serializer simply emits it; the loop is responsible for having appended that block before the next stream() (it does — see the §5 "every call gets a result" invariant).

Streaming event parse

Anthropic's stream is a sequence of typed SSE events. The adapter is a small state machine that tracks open content blocks by index and accumulates tool_use argument fragments.

async function* streamAnthropic(
  client: Anthropic, req: ProviderRequest, model: string,
): AsyncIterable<ProviderEvent> {
  const stream = client.messages.stream(
    buildAnthropicRequest(req, model),
    { signal: req.signal },                 // §7 — abort threads in here
  );

  // index -> partial tool_use being accumulated
  const pending = new Map<number, { id: string; name: string; json: string }>();
  let usage: Usage = { inputTokens: 0, outputTokens: 0 };
  let stopReason: StopReason = "end";

  for await (const ev of stream) {
    switch (ev.type) {
      case "message_start":
        // initial usage (input + any cache read/write) arrives here
        usage = mapAnthropicUsage(ev.message.usage);
        break;

      case "content_block_start":
        if (ev.content_block.type === "tool_use") {
          pending.set(ev.index, {
            id: ev.content_block.id,
            name: ev.content_block.name,
            json: "",
          });
        }
        break;

      case "content_block_delta":
        if (ev.delta.type === "text_delta") {
          yield { type: "text.delta", text: ev.delta.text };
        } else if (ev.delta.type === "input_json_delta") {
          // tool_use arguments arrive as a partial JSON string
          pending.get(ev.index)!.json += ev.delta.partial_json;
        }
        break;

      case "content_block_stop": {
        const p = pending.get(ev.index);
        if (p) {                            // a tool_use block just closed
          yield { type: "tool_call", call: {
            id: p.id, name: p.name,
            input: p.json ? JSON.parse(p.json) : {},
          }};
          pending.delete(ev.index);
        }
        break;
      }

      case "message_delta":
        // final stop_reason + cumulative output token usage
        stopReason = mapAnthropicStop(ev.delta.stop_reason);
        usage.outputTokens = ev.usage.output_tokens;
        break;

      case "message_stop":
        break;                              // stream end; emit done below
    }
  }

  yield { type: "done", stopReason, usage };
}

function mapAnthropicStop(r: string | null): StopReason {
  switch (r) {
    case "tool_use":   return "tool_use";
    case "max_tokens": return "max_tokens";
    // No canonical "stop_seq": a matched stop sequence is a normal turn end.
    case "stop_sequence":
    case "end_turn": default: return "end";
  }
}
tool_use accumulation Anthropic streams a tool call as: content_block_start (carries id + name) → one or more input_json_delta fragments (the arguments, as a partial JSON string) → content_block_stop. We only emit a tool_call at content_block_stop, once the full JSON is buffered and parsed — never on a partial fragment (§3 invariant).

05 OpenAI Responses Adapter

Backed by the openai SDK's Responses API (the decision in v0 §13 / decisions.html). Responses models a turn as an ordered list of output items; a tool call is a function_call output item, and a tool result is a function_call_output input item.

Request shaping

The system prompt maps to instructions, canonical messages flatten into the input[] array of typed items, and tools are flat objects with type: "function" and the JSON Schema under parameters. We send store: false and own conversation state ourselves (§9).

import OpenAI from "openai";

function toOpenAITools(tools: ToolSpec[]) {
  return tools.map((t) => ({
    type: "function" as const,
    name: t.name,
    description: t.description,
    parameters: t.parameters,          // same z.toJSONSchema output as Anthropic
  }));
}

// Canonical messages flatten into Responses input items.
// Note: there is no "assistant message" wrapper — text and function_call
// are sibling items in the flat input[] list.
function toOpenAIInput(messages: Message[]): OpenAI.Responses.ResponseInputItem[] {
  const items: OpenAI.Responses.ResponseInputItem[] = [];
  for (const m of messages) {
    for (const b of m.content) {
      switch (b.type) {
        case "text":
          items.push({ role: m.role, content: b.text });        // message item
          break;
        case "tool_call":
          items.push({ type: "function_call", call_id: b.call.id,
                       name: b.call.name,
                       arguments: JSON.stringify(b.call.input) });
          break;
        case "tool_result":
          items.push({ type: "function_call_output", call_id: b.id,
                       output: renderToolResult(b.result) });
          break;
      }
    }
  }
  return items;
}

function buildOpenAIRequest(req: ProviderRequest, model: string) {
  return {
    model,
    instructions: req.system,            // system prompt -> instructions
    input: toOpenAIInput(req.messages),
    tools: toOpenAITools(req.tools),
    store: false,                        // we own state — §9
    stream: true as const,
  };
}

function_call_output correlation. The call_id on the output item must equal the call_id of the originating function_call. Our canonical ToolCall.id stores exactly that value (§2), so round-tripping is a direct field copy — no provider-specific id bookkeeping leaks into the loop.

Streaming event parse

Responses emits semantic SSE events keyed by output-item index. Text streams as response.output_text.delta; tool arguments stream as response.function_call_arguments.delta; the terminal response.completed carries final status + usage.

async function* streamOpenAI(
  client: OpenAI, req: ProviderRequest, model: string,
): AsyncIterable<ProviderEvent> {
  const stream = await client.responses.create(
    buildOpenAIRequest(req, model),
    { signal: req.signal },               // §7 — abort threads in here
  );

  // output_index -> partial function_call being accumulated
  const pending = new Map<number, { id: string; name: string; args: string }>();
  let usage: Usage = { inputTokens: 0, outputTokens: 0 };
  let stopReason: StopReason = "end";

  for await (const ev of stream) {
    switch (ev.type) {
      case "response.output_item.added":
        if (ev.item.type === "function_call") {
          pending.set(ev.output_index, {
            id: ev.item.call_id, name: ev.item.name, args: "",
          });
        }
        break;

      case "response.output_text.delta":
        yield { type: "text.delta", text: ev.delta };
        break;

      case "response.function_call_arguments.delta":
        pending.get(ev.output_index)!.args += ev.delta;
        break;

      case "response.output_item.done":
        if (ev.item.type === "function_call") {
          const p = pending.get(ev.output_index)!;
          yield { type: "tool_call", call: {
            id: p.id, name: p.name,
            input: p.args ? JSON.parse(p.args) : {},
          }};
          pending.delete(ev.output_index);
          stopReason = "tool_use";        // any function_call ⇒ tool turn
        }
        break;

      case "response.completed":
        usage = mapOpenAIUsage(ev.response.usage);
        // if no tool call was seen, the completed status is a normal end
        if (stopReason !== "tool_use") {
          stopReason = ev.response.incomplete_details?.reason === "max_output_tokens"
            ? "max_tokens" : "end";
        }
        break;

      case "response.incomplete":
        usage = mapOpenAIUsage(ev.response.usage);
        stopReason = "max_tokens";
        break;
    }
  }

  yield { type: "done", stopReason, usage };
}
function_call → ToolCall A Responses tool call streams as: response.output_item.added (the function_call shell, carrying call_id + name) → repeated response.function_call_arguments.delta (argument string fragments) → response.output_item.done (item closed). As with Anthropic, we emit the canonical tool_call only at the item-done event, after parsing the buffered argument string.
Symmetry by design The two parsers are deliberately the same state machine: open item → accumulate JSON string → close item → emit. The only differences are the event names and where usage/stop_reason live. That symmetry is the payoff of the canonical ProviderEvent contract — the loop sees identical output from both.

07 Error Handling & Cancellation

Both adapters thread req.signal — the same AbortSignal the TUI raises on Ctrl-C (§5, tui.html) — directly into the SDK call's options. There is no second cancellation mechanism; one signal cancels the in-flight HTTP/SSE stream at the source.

Cancellation path

// Both SDKs accept an AbortSignal in the request options and reject the
// stream iterator with an AbortError when it fires.
const stream = client.messages.stream(body, { signal: req.signal });   // anthropic
const stream = await client.responses.create(body, { signal: req.signal }); // openai

When the signal fires mid-stream, the for await loop throws. The adapter does not let that propagate as a fatal error — an interrupt is a normal control flow event:

try {
  for await (const ev of sdkStream) { /* parse + yield, §4/§5 */ }
  yield { type: "done", stopReason, usage };
} catch (err) {
  if (req.signal.aborted || isAbortError(err)) {
    // clean unwind: report a terminal done, not an error
    yield { type: "done", stopReason: "interrupted", usage };
    return;
  }
  throw err;                  // genuine failure — bubble to the loop's error path
}

The loop then closes out the turn: any tool call already emitted still receives a result message ("interrupted by user") to keep history valid per the §5 "every call gets a result" invariant, and the AbortSignal also unwinds any in-flight Bun.spawn in the bash tool.

08 Usage / Token Accounting

Each done event carries a normalized Usage (§2). The Session accumulates it across turns and the TUI header renders it; the §9 context-limit warning reads from the same running total. Each vendor reports usage in its own shape, so each adapter has a small mapper.

// Anthropic: usage on message_start (input + cache) and message_delta (output).
function mapAnthropicUsage(u: Anthropic.Usage): Usage {
  return {
    inputTokens:     u.input_tokens,
    outputTokens:    u.output_tokens,
    cacheReadTokens:  u.cache_read_input_tokens  ?? undefined,
    cacheWriteTokens: u.cache_creation_input_tokens ?? undefined,
  };
}

// OpenAI Responses: a single usage object on response.completed.
function mapOpenAIUsage(u: OpenAI.Responses.ResponseUsage): Usage {
  return {
    inputTokens:    u.input_tokens,
    outputTokens:   u.output_tokens,
    // cached prompt tokens are nested under input_tokens_details
    cacheReadTokens: u.input_tokens_details?.cached_tokens ?? undefined,
  };
}

Accumulation rules

  • Per-turn, then summed. Usage on done is for that one provider call. The session adds it to a running total (§9's usage).
  • Input is full-history each turn. Because both providers resend full history (§6), input-token counts grow turn over turn — that is expected, and is exactly the signal the context-limit warning watches.
  • Cache fields are optional and lossy-tolerant. Anthropic distinguishes cache read vs write; Responses reports only cached (read) prompt tokens. The canonical type keeps both optional so neither mapper has to fabricate a value.
  • Anthropic splits across events. Input/cache tokens land on message_start, final output tokens on message_delta — the adapter merges them before emitting the single done (see §4).
Out of scope for v0 Cost-in-dollars estimation and per-tool token attribution are not in v0. We track raw token counts only; pricing tables and budgets are a roadmap item.

09 Open Question — store:false vs previous_response_id

This is the unresolved provider question carried from v0 §13 ("Responses statefulness"). The Responses API offers two ways to manage conversation continuity, and they are mutually exclusive in practice.

A · store:false, resend full input[]

  • We send the complete input[] every turn and set store:false so OpenAI persists nothing server-side.
  • The canonical store (§2) stays the single source of truth.
  • Symmetric with Anthropic, which has no stateful mode — one mental model, one replay path.
  • Switching providers mid-session and transcript replay both work unchanged.
  • Cost: input tokens re-sent each turn (but Anthropic does this too; §8 already accounts for it).

B · previous_response_id chaining

  • Send only the new turn's items + previous_response_id; OpenAI reconstructs prior context server-side.
  • Smaller request bodies; potential server-side prompt-cache benefit.
  • But: server now holds authoritative state we don't own — diverges from the canonical store.
  • No Anthropic analogue → two code paths, two replay stories, asymmetric error recovery.
  • A dropped id or expired response breaks the chain; reconstruction needs the full history anyway.

Recommendation

Adopt option A (store:false, own state) for v0. It is already the leaning recorded in v0 §13, and the adapter code in §5 is written for it. The provider layer's entire reason for existing is that the canonical store is authoritative and adapters are stateless translators (§1); previous_response_id would put authoritative state back on the vendor and break that invariant — reintroducing exactly the provider-specific coupling this layer is designed to eliminate. The token savings from B are real but secondary to a single, symmetric, replayable state model, and B has no Anthropic counterpart so it would only ever benefit one provider.

Decision point — confirm at M4 Validate at milestone M4 (OpenAI provider behind the same interface). If store:false request sizes or latency prove problematic at realistic context lengths, revisit B as an opt-in optimization — but only behind the same Provider interface, with the canonical store still authoritative. Until then this stays an open question, consistent with v0 §13. Track the resolution in decisions.html.
