om-cli

A custom agentic coding harness — design reference, v0.

Bun TypeScript OpenTUI Anthropic + OpenAI Draft · 2026-05-30

01 Overview & Goals

om-cli is a terminal-native agentic harness in the spirit of Claude Code / Codex: an LLM drives a loop, calls tools to read and modify the local filesystem and run commands, and a TUI renders the conversation, tool activity, and approvals.

Design goals

  • Provider-agnostic core. The agent loop is written once; Anthropic and OpenAI sit behind one interface.
  • Tools are the only side-effect surface. The model never touches the disk directly — every effect flows through a registered, schema-validated tool that goes through the permission gate.
  • Streaming-first. Text, tool calls, and tool results stream to the TUI as they arrive; nothing blocks on full completion.
  • Stop-anywhere. The user can interrupt mid-stream or mid-tool and the loop unwinds cleanly.
  • Small, legible core. v0 favors a readable single-process design over distributed/daemon architecture.
Doc role This is a living design reference for the build, not a pitch. It locks in a tight v0 and explicitly defers the rest (§2, §12).

02 v0 Scope

In scope

  • Single-turn → multi-turn agent loop with tool calling
  • Provider abstraction: Anthropic + OpenAI
  • Streaming responses to the TUI
  • Core tools: read, write, edit, ls, glob, grep, bash
  • Permission gate with allow/deny/always-allow
  • In-memory session + on-disk transcript log
  • OpenTUI shell: input box, scrollback, tool cards, approval prompt
  • Project config file + system prompt assembly
  • Ctrl-C interrupt / cancel

Deferred (post-v0)

  • MCP client / external tool servers
  • Sub-agents & parallel task fan-out
  • Context compaction / summarization
  • Hooks & lifecycle events
  • Slash-command / skill system
  • Multi-provider routing per-task
  • Persistent cross-session memory
  • Diff review UI / patch staging
v0 definition of done From a project directory, run om, type a request, and watch the agent read files, propose edits, ask for permission, apply approved changes, and run a command — end to end, with both providers selectable.

04 Architecture

One Bun process. The core is UI-agnostic and emits a typed event stream; the TUI is a consumer of that stream and a producer of user input. This boundary keeps the loop testable headless and leaves room for a future non-TUI front end.

Event stream contract

Core → TUI is a single async iterable of discriminated events. This is the seam everything hangs off of.

type AgentEvent =
  | { type: "text.delta";   text: string }
  | { type: "text.done";    text: string }
  | { type: "tool.start";   id: string; name: string; input: unknown }
  | { type: "tool.result";  id: string; output: ToolResult }
  | { type: "approval.request"; id: string; tool: string; preview: string }
  | { type: "turn.done";    stopReason: StopReason; usage: Usage }
  | { type: "error";        message: string; fatal: boolean };

05 Agent Loop

The loop is the heart of the harness: send context to the provider, stream the reply, execute any tool calls, append results, repeat until the model stops without requesting tools.

async function* runTurn(session: Session): AsyncGenerator<AgentEvent> {
  while (true) {
    const stream = provider.stream({
      system: session.systemPrompt,
      messages: session.messages,
      tools: registry.specs(),          // JSON Schema for the model
    });

    const toolCalls: ToolCall[] = [];
    for await (const ev of stream) {
      if (ev.type === "text.delta") yield ev;
      if (ev.type === "tool_call")  toolCalls.push(ev.call);
    }

    if (toolCalls.length === 0) {       // model is done talking
      yield { type: "turn.done", stopReason: "end", usage };
      return;
    }

    // Execute each requested tool (sequential in v0)
    for (const call of toolCalls) {
      yield { type: "tool.start", id: call.id, name: call.name, input: call.input };
      const decision = await permission.check(call);   // may yield approval.request
      const result = decision.allowed
        ? await registry.run(call)
        : ToolResult.denied(call);
      yield { type: "tool.result", id: call.id, output: result };
      session.appendToolResult(call, result);
    }
    // loop continues: results are now in context for the next provider call
  }
}

Loop invariants

  • Tools execute sequentially in v0. Parallel tool dispatch is deferred — it complicates approval ordering and output interleaving.
  • Every tool call gets a result message. Denied / errored / cancelled calls still append a result so provider message history stays valid (both APIs require a result for every tool call id).
  • Cancellation unwinds cleanly. An AbortSignal threads from the TUI through the provider stream and Bun.spawn; on abort the loop synthesizes an "interrupted" result for the call in flight and every remaining tool call declared in the assistant message (whether or not it had started), appends them all, then returns. This upholds the "every tool call gets a result" invariant above — leaving a sibling call unanswered would corrupt the next provider round-trip after a resume.
  • Turn cap. A max-iteration guard prevents runaway loops; hitting it emits a recoverable error.

06 Provider Layer

The single most load-bearing abstraction in v0. Anthropic and OpenAI differ in message shape, tool-call encoding, and streaming events — the provider normalizes all of it into our internal types.

interface Provider {
  readonly id: "anthropic" | "openai";
  stream(req: ProviderRequest): AsyncIterable<ProviderEvent>;
}

interface ProviderRequest {
  system: string;
  messages: Message[];        // internal canonical shape
  tools: ToolSpec[];          // internal → translated per provider
  signal: AbortSignal;
}

type ProviderEvent =
  | { type: "text.delta"; text: string }
  | { type: "tool_call";  call: ToolCall }
  | { type: "done";       stopReason: StopReason; usage: Usage };

Canonical message store The session stores messages in our internal format. Each provider has an adapter that serializes to its wire format on send and parses its stream back to ProviderEvent. We never store provider-native messages — that keeps switching providers mid-session theoretically possible and the core untangled from SDK shapes.

07 Tools

A tool is a name, a zod input schema, a permission class, and a run function. The schema is the single source of truth — it generates the JSON Schema the model sees and validates input before execution.

interface Tool<I> {
  name: string;
  description: string;
  schema: ZodSchema<I>;
  permission: PermissionClass;          // see §8
  preview(input: I): string;            // human-readable approval preview
  run(input: I, ctx: ToolContext): Promise<ToolResult>;
}

v0 tool set

ToolEffectPermission
readRead a file (with line range)read
lsList a directoryread
globFind files by pattern (Bun.Glob)read
grepSearch file contents (ripgrep if present, else fallback)read
writeCreate / overwrite a filewrite
editExact-string replacement (old_string → new_string)write
bashRun a shell command via Bun.spawnexec

Tool conventions

  • Absolute paths only at the tool boundary. v0 does not enforce a project-root jail — paths are taken as given (an out-of-root write still goes through the normal write/exec approval, so the user is the guard).
  • edit uses exact-string replacement: the file must have been read this session and old_string must match uniquely — otherwise the tool errors and asks the model to add surrounding context. Deterministic, and its failure mode is a retry, not silent corruption. Full-file creation/rewrite goes through write.
  • Results are structured: { ok, content, error?, meta? }. Large outputs are truncated with a notice before being sent to the model.
  • bash streams stdout/stderr to the TUI live and threads the AbortSignal for cancellation.
Edit strategy — post-v0 v0 commits to exact-string replacement for its determinism and zero applier complexity. The longer-term path is unified-diff / patch application, adopted alongside the deferred diff review UI — the diff format and the review surface are the same artifact, so they should land together rather than building a fuzzy patch applier before the loop is even proven. Line-range editing is rejected outright (line-number drift across multi-edit turns risks silent corruption).

08 Permissions

Every tool declares a permission class. Before a tool runs, the gate decides: auto-allow, prompt the user, or deny. Decisions can be remembered for the session.

ClassDefault policyExamples
readauto-allowread, ls, glob, grep
writepromptwrite, edit
execpromptbash
 
type Decision =
  | { allowed: true;  remember?: "session" }
  | { allowed: false; reason: string };

interface PermissionGate {
  // emits approval.request to the TUI when interaction is needed
  check(call: ToolCall): Promise<Decision>;
}

Behavior

  • Three responses in the approval modal: Allow once, Allow for session, Deny.
  • Session allowlist keyed by tool name + (optionally) a normalized argument signature (e.g. allow bash: npm test without re-prompting).
  • Config can pre-allow classes or specific commands (§11), mirroring the fewer-permission-prompts idea.
  • Deny still returns a tool result so the model can adapt rather than the loop stalling.
Deferred Fine-grained per-path write scopes, command argument parsing/sandboxing, and a "plan mode" (read-only) toggle are post-v0. v0 relies on coarse classes (read / write / exec) plus the approval prompt — there is no project-root path jail; the user approving a write/exec is the boundary.

09 Sessions & Context

A session owns the canonical message list, the assembled system prompt, usage accounting, and the session allowlist. v0 keeps the live session in memory and appends an on-disk transcript for replay/debugging.

class Session {
  messages: Message[] = [];
  systemPrompt: string;
  usage: Usage = zeroUsage();
  allowlist: Set<string>;

  append(msg: Message): void;
  appendToolResult(call: ToolCall, r: ToolResult): void;
  // transcript: append-only JSONL written alongside each mutation
}

System prompt assembly

Built once per session from, in order: base harness instructions → environment block (cwd, OS, date, git status) → project OM.md if present → tool usage notes. Mirrors how Claude Code composes its prompt.

Context handling in v0

  • No compaction yet. v0 simply tracks token usage and warns near the model's context limit.
  • Transcript log: .om/transcripts/<session-id>.jsonl — every message, tool call, and result, append-only.
  • Resume is a stretch goal: replay the JSONL to rebuild messages.
Deferred Summarization/compaction at context pressure, cross-session memory, and semantic file indexing are post-v0.

10 TUI Layer (OpenTUI)

The TUI consumes the core's AgentEvent stream and renders four regions. It owns no business logic — it renders state and forwards input + approval responses.

Applying edit: │ │ ┌── edit src/parser.ts ───────────────┐ │ │ │ - if (c === '"') … │ │ │ │ + if (c === '"' || c === "'") … │ │ │ └────────────────────────────────────────┘ │ ├────────────────────────────────────────────────┤ │ Allow edit to src/parser.ts? (y) once (a) session (n) │ approval ├────────────────────────────────────────────────┤ │ > _ │ input └────────────────────────────────────────────────┘

Regions

  • Header — project path, active provider/model, token usage.
  • Scrollback — interleaved user text, streamed assistant text, and collapsible tool cards (name, args summary, result/preview).
  • Approval bar — appears on approval.request; keybound y / a / n; blocks the loop until answered.
  • Input — multiline prompt; Enter sends, Ctrl-C interrupts the active turn, Ctrl-D exits.

Rendering rules

  • Streaming text appends to the live assistant block on each text.delta.
  • Tool cards render on tool.start (spinner) and update in place on tool.result.
  • bash output tails live inside its card.
  • The TUI never mutates session state — it sends an approval response or user message back into the core.

Still open

  • TUI state model: does OpenTUI's reactivity handle a long, mutating scrollback efficiently, or do we need windowed rendering early? (Validate at M5.)
  • Responses statefulness: use store:false and own conversation state ourselves (keeps the canonical store authoritative and providers swappable) vs leaning on OpenAI's previous_response_id. Leaning toward owning state — confirm at M4.
